# CLASSROOM ERP — ATTENDANCE SECURITY ARCHITECTURE
## Anti-Proxy, Cryptographic Rotation & Multi-Tenant Defense-in-Depth

---

### 1. Threat Modeling & Countermeasure Matrix

| Threat Vector | Attack Scenario | Antigravity Defense Countermeasure | Security Layer |
|---|---|---|---|
| **QR Screenshot Sharing** | Student takes photo or screenshot of projected QR code and shares via WhatsApp/Telegram to remote friends. | Short-window cryptographic rotation (15–45s). Old tokens rejected with sliding-window HMAC expiration. | Cryptographic Token Layer |
| **Remote Geofence Spoofing** | Student uses mock GPS app or developer mode to fake coordinates inside classroom. | Dual-factor binding: GPS combined with physical Web Bluetooth (BLE) Beacon RSSI check. Mock location detection flags. | Physical Hardware Layer |
| **Token Replay Attack** | Malicious actor captures valid QR token from network stream and attempts multiple submissions. | Cryptographic nonce tracked per rotation; database compound key `@@unique([sessionId, studentId])` rejects duplicate attempts. | Transport & Database Layer |
| **Cross-Course Proxy** | Student from Section B attends Section A and attempts to record attendance for peer. | Server checks active enrollment record in `Enrollment` table for `[studentId, courseId]`. Unenrolled scans rejected with `403 Forbidden`. | Business Authorization Layer |
| **Cross-Tenant Breach** | Student from University A attempts to scan attendance token generated by University B. | JWT token contains `institutionId`. Session query strictly asserts `session.course.department.institutionId === auth.institutionId`. | Multi-Tenant Isolation Layer |
| **Client-Side Identity Tampering** | Attacker modifies `studentId` in HTTP request body to credit a friend. | `studentId` in request payload is strictly ignored for students; resolved exclusively from validated server-side JWT session cookie. | Authentication Layer |
| **Token Brute-Forcing** | Automated script sends rapid guesses of QR token parameters. | Token is 64-character SHA-256 HMAC with high-entropy cryptographic nonce; rate limited per IP and per authenticated user. | Network & Gateway Layer |

### 2. Cryptographic QR Token Structure (`APX_ATT_V2`)

Tokens are structured into six dot-delimited segments:

```
APX_ATT_V2.<sessionId>.<cryptoNonce>.<issuedAt>.<expiresAt>.<hmacSignature>
```

1. **`APX_ATT_V2`**: Protocol version identifier.
2. **`sessionId`**: UUID of the active `AttendanceSession`.
3. **`cryptoNonce`**: 16-byte random hexadecimal string generated via `crypto.randomBytes(16)`.
4. **`issuedAt`**: Unix epoch timestamp (seconds) of token creation.
5. **`expiresAt`**: Unix epoch timestamp (seconds) after which token is considered expired (default: `issuedAt + rotationSeconds`).
6. **`hmacSignature`**: Constant-time cryptographic signature generated using `HMAC-SHA256(secretKey, `${sessionId}.${cryptoNonce}.${issuedAt}.${expiresAt}`)`.

#### Cryptographic Verification Rules:
- Server calculates expected signature and compares using `crypto.timingSafeEqual` to eliminate timing attack vectors.
- If `now > expiresAt + SLIDING_WINDOW_TOLERANCE` (5 seconds grace for network transit), verification immediately fails.

### 3. Server-Side Geofencing Verification (Haversine Formula)

The ERP never trusts a client-side `inGeofence: true` flag. The client provides its raw coordinates `(lat_s, lng_s)` and accuracy. The server computes great-circle distance to the room's registered coordinates `(lat_r, lng_r)`:

$$\Delta\phi = \frac{\pi}{180} (\text{lat}_r - \text{lat}_s), \quad \Delta\lambda = \frac{\pi}{180} (\text{lng}_r - \text{lng}_s)$$
$$a = \sin^2\left(\frac{\Delta\phi}{2}\right) + \cos\left(\frac{\pi}{180} \text{lat}_s\right) \cos\left(\frac{\pi}{180} \text{lat}_r\right) \sin^2\left(\frac{\Delta\lambda}{2}\right)$$
$$d = 2 \cdot R \cdot \text{atan2}(\sqrt{a}, \sqrt{1 - a}) \quad (R = 6,371,000 \text{ m})$$

- If $d > \text{allowedRadiusMeters}$ (e.g. 100m), verification is rejected with `403 Forbidden`.
- **Location Privacy Compliance**: To protect student privacy under GDPR and FERPA, raw student GPS coordinates are never persisted in the database; only the calculated distance metric (`distanceMeters`) and the verification boolean (`geofenceVerified`) are stored.

---

### 4. Web Bluetooth (BLE) Proximity Verification

- Each smart classroom is equipped with a registered Bluetooth beacon advertising a dedicated Service UUID.
- During attendance verification, if `bleRequired === true`, the student's browser must execute a challenge-response handshake with the classroom beacon.
- Server validates that the reported signal strength (RSSI) is stronger than the calibrated room perimeter threshold (e.g. RSSI > -80 dBm), confirming physical presence within the room walls.

### 5. Audit Logging & Non-Repudiation

Every security-sensitive attendance event is written to `AuditLog`:
- `ATTENDANCE_SESSION_CREATED`
- `ATTENDANCE_SESSION_STARTED`
- `ATTENDANCE_TOKEN_ROTATED`
- `ATTENDANCE_RECORDED`
- `ATTENDANCE_DUPLICATE_BLOCKED`
- `ATTENDANCE_GEOFENCE_FAILED`
- `ATTENDANCE_SESSION_CLOSED`
- `ATTENDANCE_SESSION_LOCKED`
- `ATTENDANCE_CORRECTION_FILED`
- `ATTENDANCE_CORRECTION_RESOLVED`
